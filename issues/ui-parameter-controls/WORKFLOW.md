# Протокол исполнения

Версия: **1.0**. Основание: AI-ORCHESTRATOR 2.1. Применяется ко всем задачам инициативы `ui-parameter-controls`. Исходный шаблон на рабочем столе для исполнения не требуется.

## Начало работы

1. Прочитать выбранную issue, этот протокол, [реестр](README.md), корневой [AGENTS.md](../../AGENTS.md) и перечисленные в задаче документы до выполнения.
2. Проверить рабочее дерево, HEAD, применимые локальные инструкции, входы и результаты зависимостей. Сохранить чужие изменения, включая существующее изменение корневого README.md.
3. Найти незавершённые пункты своего назначения в пределах поручения. Sol означает GPT-6.1 Sol, Luna — GPT-6 Luna. Назначение в файле не переключает модель. При неопределённом назначении уточнить маршрутизацию перед реализацией.
4. Проверить условия допуска. При существенном расхождении кода с планом записать его; не исполнять устаревший контракт молча.
5. Выполнять доступные пункты, повторно проверять зависимости после завершения. Не переходить к другой issue без поручения.

## Подготовка и передача

P выполняется назначенным исполнителем после поручения, а не при создании плана. P закрывается, когда принимающий T имеет конкретные версии входов/API, примеры входа и результата, проверенную команду или процедуру проверки, границы решений и оставшиеся зависимости. Для реализации достаточно готового контракта; реализовывать T внутри P не нужно. Предлагаемые контракты в issue предварительны до P. Если нужен ответ пользователя, остановить зависимые пункты, сохранив независимую работу.

Q проверяет обязательные AC, интеграцию и доказательства после T; она не заменяет собственные проверки исполнителя T. В простых задачах без P/Q итоговую приёмку делает указанный исполнитель. Зависимости передаются только через сохранённый артефакт или журнал, не через историю чата.

- Проверять результат до передачи. При неожиданном результате сохранить диагностику и остановить только зависимую работу; назвать недостающий вход/решение и продолжать независимые разрешённые пункты.
- Не повторять подтверждённые проверки без причины: изменения входов, кода, контракта, окружения, дефект или недостаточность доказательств.

## Статусы

| Статус | Условие |
| --- | --- |
| open | Исполнение не начато; зависимости перечислены отдельно |
| in_progress | Есть выполненная часть, работа или передача |
| blocked | Для всей оставшейся работы нужен недоступный вход/решение; доступных пунктов нет |
| completed | Все обязательные пункты и AC подтверждены актуальными доказательствами, включая Q |

Ожидание следующей модели не является блокировкой. Частичную блокировку фиксировать у пункта, продолжая доступные работы. Источник состояния — issue; README синхронизировать после изменения статуса или доступности следующей задачи. Журнал хранит историю, а не заменяет текущее состояние.

## Журнал и завершение

Каждая новая запись содержит: дату и назначенного исполнителя; завершённые P/T/Q-ID; изменённые файлы и артефакты; версию кода, входов и окружения; команды/процедуры и фактические результаты; подтверждённые AC и доказательства; ограничения; следующего исполнителя, доступные ID, точные входы и команды; остаток и общий статус. Прежние записи не стирать. Время указывать только если измерено.

Для небольших результатов достаточно журнала. Контракты сохранять по указанным будущим путям; пустые отчёты не создавать. Подробные отчёты при необходимости помещать в `results/` этой инициативы, тяжёлые результаты — вне каталога текстовых задач.

Назначенный принимающий проверяет все обязательные критерии и Q, затем ставит completed и обновляет README. Наличие файлов или завершение работы одной модели не доказывает готовность всей issue. В ответе перечислить выполненные ID, проверки, остаток, следующего исполнителя и статус. При полном завершении предложить сообщение коммита на английском в Conventional Commits; не создавать коммит без поручения. Локальные ISSUE-ID не считать номерами GitHub. Не публиковать задачи без прямого поручения.
